# v0.3 architecture decision — minimum justified complexity

Status: recommendation from executed evidence; **v0.3 has not been implemented or released**.
Evidence: [benchmark report](../benchmarks/v0.2/report.md), baseline v0.2.1 at
0bc6e1d2fa2c696ce050e82035e9b3f5b6d411e7, measured harness at
7dfb173a0d1cef3a30a4ae6e24998614da282fe0. The owner supplied no absolute latency SLO,
concurrent-dataset target, durability requirement or independent algorithm scaling requirement.
Two million values means one dataset; it is not evidence that two services are necessary.

## Evidence and assumptions

On this desktop, two-million-value MIXED IQR averaged 548.925 ms/op versus 155.754 for Z-Score;
allocation was 115.954 versus 100.507 MiB/op. Favorably ordered IQR was 111.388 ms/op with nearly
the same allocation. The FULL API responses were 9,900,170 bytes each; medians over only three
serial samples were 730.644 / 405.794 ms. The API process peaked at 1,179.594 MiB working set
with a 2 GiB heap cap. This is exploratory single-dataset evidence, not a concurrency capacity
test, production-ready threshold, stable p99, per-request heap bound or isolated CPU profile.

The source still sorts IQR's full copy (general O(n log n)) and scans for Z-Score (O(n)). Both
allocate/copy O(n) inputs/results. Additional JSON/transport work matters, but a precise phase
breakdown was not profiled. Any proposal must preserve global quartiles, population variance,
strict boundaries, original order, duplicates, default FULL output and existing errors/warnings.

## Recommendation and primary measurable improvement

Keep **one stateless modular application** with the existing Strategy registry. It can be
replicated as a whole if future load evidence warrants it. Independent per-algorithm services,
RabbitMQ and gRPC add operational cost without evidence that they improve the present requirement.

The primary v0.3 performance experiment should **reduce allocated bytes per two-million-value
calculation**. Prototype primitive value storage at the parsing/core boundary and avoid repeated
per-value boxing/copies where a small readable implementation permits. Keep typed results and
the public HTTP contract; do not replace correctness with a quickselect or streaming framework
as part of this first experiment. Compare GC-profiler B/op, ms/op and process memory against the
recorded baseline on identical fixtures/heap/JDK, with longer warmup and forks if budget permits.

Success means a reproducible allocation reduction while exact statistics/partitions remain valid
and the full regression/coverage gate stays green. An absolute latency promise or arbitrary owner
SLO is not invented here. Stop/reassess if complexity grows without a measured gain. This work
targets processing **one dataset**; a worker pool alone does not make its sort asymptotically faster.

## Required bounded scope for an authorized v0.3

1. Preserve the existing API and exact mathematical convention; test first, retain 100% combined
   LINE/BRANCH coverage, and rerun the same baseline-comparable measurements after any prototype.
2. Add explicit admission/overload policy before expensive body materialization. Bound active work
   and any queue; do not queue many decoded 2M-value lists in memory. Select actual byte/value
   limits and overload responses with the owner once supported sizes/SLOs are agreed.
3. Start with the existing synchronous request path plus a simple admission limit; use a bounded
   worker executor only if scheduling/queuing semantics require one. Configure worker count from
   measured concurrent-dataset memory and CPU behavior rather than logical-core count alone.
4. Run a separate bounded load test at increasing active datasets, including request/response bytes,
   queue time, accepted/rejected requests, memory, GC and properly sampled latency percentiles.
   Current three-sample API observations cannot establish overload behavior or tail latency.

Global statistics remain global. Do not average chunk quartiles or classify chunks against their
own unrelated local fences. Dataset-level parallelism operates on independent complete datasets.

## Conditional follow-ups

| Candidate | When justified | Present decision |
| --- | --- | --- |
| Docker/resource limits | Reproducible packaging/deployment and realistic constrained load tests | Reasonable optional packaging. Cap heap and leave native/thread/code headroom; observed RSS is not a safe hard limit. Retest CPU/memory quotas; this run had no container/CPU quota. |
| Optional smaller output | Consumers genuinely do not need all normalValues | Propose an explicit opt-in/versioned summary or result retrieval mode. Preserve default FULL behavior. Most values here are normal, so bytes may fall substantially, but no latency gain is measured yet. |
| Dataset/result storage | Payload reuse, retained results, async jobs or recovery is required | Define retention, ownership, privacy and cleanup first; no storage layer now. |
| RabbitMQ | Durable async backlog, decoupled jobs, retries and recovery are business requirements | Not required for one synchronous dataset. Adds broker operations, idempotency, retries, DLQ and integration tests. |
| gRPC | A measured internal service boundary needs it | No boundary is justified now. Do not assume packed doubles reduce bytes for these short decimal fixtures; transport alternatives were not benchmarked. |
| Authentication | Deployment/trust boundary requires protected datasets or access control | Security requirement, not a sorting speed optimization. Clarify before external exposure; it was outside this local benchmark. |
| Independent algorithm services | Sustained differing SLOs/load/ownership/rollout needs justify independent scaling | Require workload/concurrency evidence. Separate deployments add network contracts, failure handling, tracing, auth, orchestration and cross-service tests. They do not reduce algorithmic complexity. |

## Budget and evidence gate

A focused allocation prototype, bounded admission policy, regression/coverage checks and repeat
measurements are the defensible scope for the remaining approximately 60-minute v0.3 allocation,
subject to the next owner's actual prompt. If that scope does not fit, preserve progress and report
partial results. Do not try to add a broker, persistence, gRPC, auth and multiple deployments merely
to demonstrate names in an interview. Packaging and broader load studies can follow separately.

The benchmark evidence gate is satisfied by actual core/API executions and saved raw data, with
the limitations above. Implementation still requires the conditional next prompt; no v0.3 work
was started automatically. Prerequisite/result: AD-RES-20261110-003.
