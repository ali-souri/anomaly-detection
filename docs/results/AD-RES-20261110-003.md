## Interpretation and v0.3 recommendation

Source review establishes IQR's general O(n log n) copy-sort plus linear classification, and
Z-Score's O(n) passes. Both retain/allocate O(n) input/output structures. Timing ratios alone are
not an asymptotic proof. MIXED IQR's much larger time versus ordered IQR, with similar B/op,
supports sorting as a material cost. Both algorithms' 100â€“116 MiB/op allocation and GC activity
also support an allocation-focused next experiment. API costs include large full JSON payloads;
a precise phase attribution was not profiled, so the API/core gap is treated as an inference.

The simplest defensible next architecture is **one stateless modular application**, with a
primary measurable prototype to reduce per-dataset allocated bytes while preserving results and
the default FULL HTTP contract. Add bounded admission before expensive parsing and test concurrent
datasets to choose limits/worker count. A worker pool handles more independent datasets; it does
not make one sort cheaper. Microservices do not reduce algorithmic complexity.

There is no owner latency SLO or concurrency target. Independent algorithm deployments, RabbitMQ,
storage, gRPC and auth remain conditional on real scaling/durability/security needs. Docker/resource
caps and optional smaller output need separate tests, not invented performance guarantees. Never
average chunk quartiles or classify chunks against unrelated local statistics. Required/optional
work and the remaining approximately 60-minute v0.3 scope are detailed in the
[architecture decision](../decisions/v0.3-architecture.md). No conditional v0.3 task was started.
